---
title: 'Strict core vs MCP-B extensions'
description: 'Why the WebMCP core stays small and which capabilities MCP-B layers around it.'
keywords: ['webmcp core', 'mcp-b extensions', 'document.modelContext']
icon: 'diagram-venn'
---

The standards-owned WebMCP core publishes tools through
`document.modelContext`: `registerTool()`, `getTools()`, and `ontoolchange`.
Keeping that core small makes it portable across native browser
implementations, strict polyfills, and libraries that only need to expose
tools. Chrome's optional `executeTool()` method is an implementation extension,
not part of this core.

`@mcp-b/webmcp-types`, `@mcp-b/webmcp-polyfill`, and `usewebmcp` stay close to
this portable surface.

MCP-B adds `listTools()`, prompt and resource registration, browser transports,
and a composed official MCP server. `BrowserMcpServer`, `@mcp-b/global`, and
related packages own these additions. They are not standard WebMCP methods.

The composed server is available through `BrowserMcpServer.mcpServer`.
Protocol-version-specific SDK features, including elicitation and deprecated
sampling, stay behind that boundary. They are not methods on
`document.modelContext` or direct `BrowserMcpServer` helpers.

Libraries and sites that only publish tools should target the strict core.
The standard can expose tools across a document tree with permissions and
origin controls. Applications that also need namespaced iframe routing,
prompts, resources, relays, desktop clients, or full MCP transport use the MCP-B
extension layer.
This boundary preserves runtime portability.
