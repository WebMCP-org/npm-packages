## Inspect registered tools

Open the browser console and check whether `document.modelContext` is available:

```js title="Browser console"
console.log('modelContext:', typeof document.modelContext);
```

If it returns `"object"`, the runtime is loaded. List registered tools:

```js title="Browser console"
const tools = await document.modelContext.getTools();
console.log(
  'Registered tools:',
  tools.map((t) => t.name)
);
```

## Execute a tool manually

Call any registered tool from the console to verify it works in isolation:

```js title="Browser console"
const modelContext = document.modelContext;
const tools = await modelContext.getTools();
const tool = tools.find((candidate) => candidate.name === 'my_tool');
if (!tool) throw new Error('my_tool is not registered');

const executeTool = modelContext.executeTool;
if (typeof executeTool !== 'function') {
  throw new Error('This runtime does not expose the optional Chrome executeTool extension');
}

const result = await executeTool.call(modelContext, tool, '{"query": "test"}');
console.log('Result:', result);
```

`executeTool()` is a Chrome extension rather than part of the strict WebMCP
core, so always feature-detect it. If it is unavailable, use the Model Context
Tool Inspector or an MCP client connected through your runtime. A direct call
removes the MCP transport from the path, but invalid input, a stale descriptor,
an aborted registration, access checks, navigation, or the handler itself can
still reject.

## Use Chrome DevTools MCP for debugging

The upstream `chrome-devtools-mcp` package can inspect the page, list WebMCP tools, execute them, and read browser console messages. See [Use Chrome DevTools MCP](/how-to/use-devtools-mcp) for setup.

Once configured, ask your MCP client:

```text title="Prompt"
Navigate to http://localhost:3000, call list_webmcp_tools, and report any browser console errors.
```

The agent can then call `execute_webmcp_tool` with a listed tool name and JSON-stringified test input.

## Use the Model Context Tool Inspector

Chrome's WebMCP documentation recommends the [Model Context Tool Inspector](https://chromewebstore.google.com/detail/webmcp-model-context-tool/gbpdfapgefenggkahomfgkhfehlcenpd) extension. Install it from the Chrome Web Store, then open its side panel on any page to see registered tools and execute them with JSON input. It is a community tool, not an officially supported Google product.

<Note>
  Use a current Chrome channel that exposes "WebMCP for testing" in `chrome://flags`. The inspector
  observes the current `document.modelContext` surface.
</Note>

## Detect native vs. polyfill

Determine which implementation is active:

```js title="Browser console"
if (!document.modelContext) {
  console.log('No modelContext: polyfill not loaded');
} else if (document.modelContext.__isWebMCPPolyfill === true) {
  console.log('Polyfill detected');
} else {
  console.log('Native API');
}
```

`__isWebMCPPolyfill` is an MCP-B diagnostic marker, not a standard API. Do not
use it to choose application behavior.

## Common failures

### `document.modelContext` is `undefined`

The polyfill has not loaded, or it loaded after your code ran.

<Steps>
  <Step title="Verify the import exists">
    Confirm your entry point imports `@mcp-b/global`, or explicitly initializes the strict polyfill:

    ```ts
    import { initializeWebMCPPolyfill } from '@mcp-b/webmcp-polyfill';

    initializeWebMCPPolyfill();
    ```

  </Step>
  <Step title="Check import order">
    Runtime initialization must finish before code calls `document.modelContext`. Keep it at the top
    of your entry file.
  </Step>
  <Step title="For script tags, check load order">
    Place the `@mcp-b/global` script tag before any script that registers tools.
  </Step>
</Steps>

### Chrome flags not enabled (native API)

If you are testing the native browser API without the polyfill, enable the experimental flag.

Navigate to `chrome://flags/#enable-webmcp-testing`, set **WebMCP for testing**
to **Enabled**, and relaunch Chrome. See [Try the native Chrome
preview](/tutorials/first-native-preview) for the complete manual setup.

### Tools not appearing in the agent

<Steps>
  <Step title="Verify tools are registered">
    Run `await document.modelContext.getTools()` in the console. If the list is empty, your
    `registerTool` calls have not executed yet.
  </Step>
  <Step title="Check transport connection">
    If you use a browser extension or local relay, confirm it is running and connected. For the
    local relay, run `webmcp_list_sources` from your MCP client.
  </Step>
  <Step title="Check registration timing">
    If tools register after the client queries them, re-run discovery or observe the `toolchange`
    event. MCP-B bridges subscribe to changes, but a custom one-shot consumer must query again.
  </Step>
</Steps>

### Schema validation errors

The `inputSchema` must be JSON-serializable JSON Schema. Object and array roots are both supported:

```js title="Schema examples"
// Object input
inputSchema: {
  type: 'object',
  properties: { query: { type: 'string' } },
  required: ['query']
}

// Array input
inputSchema: {
  type: 'array',
  items: { type: 'string' }
}
```

If a schema cannot be serialized, registration rejects. Input validation behavior depends on the runtime and invocation path; see [Use Schemas and Structured Output](/how-to/use-schemas-and-structured-output).

### Duplicate tool names

Calling `registerTool` with a `name` that is already registered returns a
rejected promise. To replace a tool, abort the previous registration signal
first, then await the new registration. Use unique, descriptive names like
`search_products` or `search_docs` to avoid collisions across components.

### Local relay not discovered

| Symptom                | Fix                                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `No sources connected` | Confirm the page loaded `embed.js` and the relay process is running on the expected port (default: 9333).                                  |
| `No tools listed`      | Confirm tools are registered on `document.modelContext` and that discovery sees them. The embed subscribes to `toolchange` and also polls. |
| `Tool not found`       | The tab may have reloaded or disconnected. Call `webmcp_list_tools` again to refresh.                                                      |
| Connection blocked     | Verify `--widget-origin` matches your host page origin, and the relay port matches the `data-relay-port` attribute on the embed script.    |

See [Connect Desktop Agents with Local Relay](/how-to/connect-desktop-agents-with-local-relay) for full setup instructions.

### Transport origin mismatch

When using `@mcp-b/transports` with `TabServerTransport` or iframe transports, the `targetOrigin` and `allowedOrigins` settings must match.

Set `targetOrigin` to the exact origin of the receiving window (for example, `https://myapp.com`). Set `allowedOrigins` on the server side to accept messages only from trusted origins. Using `"*"` disables origin checking and is appropriate only during development.

See [Transports and Bridges](/explanation/architecture/transports-and-bridges) for how origin validation works across transport types.

### WebMCP not detected (Chrome DevTools MCP)

The `list_webmcp_tools` tool returns "WebMCP not detected" when Chrome's native
WebMCP registry is unavailable or empty. MCP-B tools appear when
`@mcp-b/global` adopts and mirrors that native context; the standalone
JavaScript polyfill is not a Chrome DevTools discovery source.

<Steps>
  <Step title="Confirm the page exposes WebMCP">
    In the page console, inspect `document.modelContext` and run `await
    document.modelContext?.getTools()`.
  </Step>
  <Step title="Navigate and re-check">
    After navigating to a page with tools, call `list_webmcp_tools` again.
  </Step>
  <Step title="Check the console for errors">
    Use `list_console_messages` in your MCP client to see if tool registration threw an error.
  </Step>
</Steps>
